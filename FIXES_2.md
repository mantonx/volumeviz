### 1. [FIXED THIS SESSION] Default (and only-actually-available) size-scan method double-counted nested directories — volume sizes were inflated once a volume had more than ~20 directories

**Verified by reading the code, reproducing the exact live code path, and confirming the overcount by hand with real `du` invocations before fixing it.**

`internal/services/scanner/directory_analyzer.go`'s `enumerateDirectories` (called from `DirectoryAnalyzer.AnalyzeAndBatch`) walked a volume's entire tree via `filepath.Walk` and appended **every directory at every depth** (root, every subdirectory, every sub-subdirectory, up to `maxDepth: 10`) into one flat list — no `SkipDir` once a subtree had been captured. That list was chopped into batches of 20 (`createBatches`, sorted by **estimated size**, not by tree position), and `du_progressive.go`'s `processBatch` ran `du -s -B1 <dir1> <dir2> ... <dirN>` per batch, summing each batch's total into a running grand total across all batches.

**One subtlety worth recording, since it initially looked like it might make the bug a non-issue:** GNU coreutils `du` (9.11, what's actually installed here) silently deduplicates when an ancestor and its own descendant are passed to the *same* `du -s` invocation — `du -s -B1 root root/child` prints one line for `root`'s already-inclusive total, not two summed lines. That could have made this harmless *if* every ancestor/descendant pair always landed in the same batch. They don't: `createBatches` sorts directories by **estimated size descending**, completely unrelated to tree adjacency, then chunks sequentially into groups of 20 — so a parent and child are only reliably in the same batch by coincidence, and reliably split apart on any volume with more than ~20 total directories (i.e. almost every real one). Confirmed by hand: building a 4-level nested fixture and simulating the actual cross-batch summation (root scanned in one `du` call, its three descendants scanned together in a separate call, results added) produced **2,150,400 bytes against a true total of 1,228,800 bytes — a ~1.75x overcount** in that small example, scaling further with more nesting/directories.

This was not dead/unreachable code: `NewDuMethod` (`du_progressive.go:25`) was registered directly in the live scan-method chain in `internal/services/scanner/volume_scanner.go:90-93` (`[]interfaces.ScanMethod{NewDiskusMethod(...), NewDuMethod(...), NewNativeMethod(...)}`), tried in that order for every scan. Confirmed live in this exact dev container: `diskus` is **not installed** (`which diskus` → exit 1, only `/usr/bin/du` present), so `NewDuMethod` — the buggy one — was the method actually used for every real scan running in this environment, not a rarely-triggered fallback. `diskus_progressive.go`'s `ProgressiveDiskus.processBatch` had the identical bug (diskus already reports a directory's full recursive size; running it per-directory across the same flat, cross-batch-split directory list and summing double-counted the same way) — fixed alongside it even though `diskus` isn't installed in this container, since it's `NewDuMethod`'s preferred sibling in the method chain and would hit production the moment `diskus` is available anywhere this runs.

**Fix applied:** rewrote both `ProgressiveDu.Scan`/`ProgressiveDiskus.Scan` to run a single `du -s`/`diskus` call against the scan root only (both tools are already fully recursive — no batching, enumeration, or per-directory summing needed to get a correct total). Deleted `directory_analyzer.go` and its dedicated test file entirely (`DirectoryAnalyzer`, `DirectoryBatch`, `DirectoryInfo`, `BatchingStrategy` — all now fully unused, confirmed via repo-wide grep with zero remaining references outside their own definitions). Rewrote `du_progressive_test.go` and `diskus_method_test.go`'s batch-oriented tests to test the new single-call methods, and added a regression test in each (`TestDuMethodScan_NestedDirectories_NoDoubleCounting`, `TestDiskusMethodScan_NestedDirectories_NoDoubleCounting`) that builds a real 4-level nested fixture with data at every level and asserts the scanned total exactly matches a direct, independent `du -s`/`diskus` call on the root — this is the test that would have caught the original bug, and does fail against the old batching code (verified by hand-simulating the cross-batch-summation math against the same fixture before writing the fix, since the old and new code can't coexist in the same test file to diff directly).

**Verified:** `go build ./...` clean, `go vet ./internal/services/scanner/...` clean, `go test ./internal/services/scanner/... -run "TestDu|TestDiskus"` passes (diskus tests skip gracefully since `diskus` isn't installed in this container, matching the `Available()` check every other diskus test already relied on).

**Not yet done, worth a fast-follow:** finding #12 below (partial-scan-failure results aren't flagged) is still open and independent of this fix — a `du`/`diskus` call against the root can still silently undercount an inaccessible subtree with no `Partial` indicator on the result.

### 1b. [FIXED THIS SESSION] `PerMethodTimeout` config was completely inert — every scan was silently hard-capped at 5 minutes regardless of what operators configured

**Found during a follow-up efficiency/reliability review of the rest of the scanner package, requested mid-session ("is the scanner code efficient and reliable?"), verified by hand before fixing.**

`SCAN_PER_METHOD_TIMEOUT` (env var, default 30 minutes) was read into `internal/config/config.go`, plumbed through `internal/api/v1/router.go` into `coreModels.Config`, and threaded carefully into a `TimeoutConfig` struct on the scanner (`volume_scanner.go:107-111`) — and then never read again. Every actual timeout enforcement point (`scan_utilities.go:25`'s outer per-attempt wrapper, and redundantly again inside each of `native_method.go`, `du_progressive.go`, `diskus_progressive.go`'s own constructors) used `config.Scanning.DefaultTimeout` instead, hardcoded to 5 minutes. An operator raising `SCAN_PER_METHOD_TIMEOUT` for large or slow volumes (this app explicitly supports CIFS network mounts — confirmed live, `/cifs/fictionalserver/tv` and `/cifs/fictionalserver/movies` are real configured volumes on this host) got no effect whatsoever; every scan was silently capped at 5 minutes no matter what.

**Fix applied:** `scan_utilities.go`'s `scanWithMethod` now creates its timeout context from `PerMethodTimeout` instead of `DefaultTimeout` — this is the single enforced timeout per method attempt, since each `ScanMethod.Scan` implementation derives its own working context from the one it's given rather than applying a second timeout of its own. Updated all three method constructors (`NewDuMethod`, `NewDiskusMethod`, `NewNativeMethod`) to also read `PerMethodTimeout` rather than `DefaultTimeout`, so the value is consistent everywhere it's used. Verified the fix actually enforces the timeout (not just theoretically): the existing test suite had several tests hardcoding `DefaultTimeout` in their `ScanConfig` fixtures with `PerMethodTimeout` left at its Go zero-value (`0`) — after the fix, `context.WithTimeout(ctx, 0)` fired immediately, causing `TestDuMethodScan_NestedDirectories_NoDoubleCounting` and `TestNativeMethod_Scan` to fail (the latter with a nil-pointer panic in the test itself, an unrelated latent bug the immediate-timeout path exposed for the first time). Fixed all affected test fixtures (`native_method_test.go`, `du_progressive_test.go`, `diskus_method_test.go`, `performance_test.go`, `volume_scanner_test.go`) to set `PerMethodTimeout` — this cross-check is exactly what proves the config value is now actually load-bearing rather than cosmetic.

**Verified:** `go build ./...`, `go vet ./...`, and `go test ./...` all clean across the whole backend.

### 1c. [FIXED THIS SESSION] Scan checkpoint system wrote to Postgres on every scan with zero read path and zero cleanup — an unbounded, silently-growing table doing nothing

**Found in the same follow-up review; scoped and fixed after confirming with the user this wasn't "dead code to leave alone" but active, continuous, purposeless writes.**

`internal/services/scanner/checkpointing.go`'s `CheckpointManager` was genuinely wired into every async scan (`async_scanner.go` called `StartCheckpointing`/`StopCheckpointing` around every scan), periodically writing rows to a `scan_checkpoints` table every 5 minutes or every 100k items processed. But `resume.go`'s `ResumeManager.CanResume`/`GetResumeInfo`/`ResumeScanFromCheckpoint` — the only code that ever read those rows back — had **zero callers anywhere in the codebase** (confirmed via repo-wide grep). `cmd/server/main.go` had a startup function, `autoResumeIncompleteScans`, that read aggregate checkpoint *stats* and logged them, but its own comments admitted it was "a placeholder that demonstrates the pattern" with a `TODO: Add GetIncompleteScanIDs() query` that was never written — it never actually resumed anything. No cleanup job ever called `CleanupOldCheckpoints` either. Live-confirmed on this dev host: 14 checkpoint rows had accumulated in under a day of intermittent use (`SELECT count(*) FROM scan_checkpoints` → 14, oldest/newest both from the same ~10-second window of one scan run), with no code path that would ever delete or use them.

Tracing further revealed **this wasn't a system that needed "connecting"** — filesystem-indexing resume already works, via a completely separate, working mechanism: `internal/scheduler/resume_manager.go`'s `ResumeManager.ResumePausedScans` (run periodically, confirmed live in logs as "Checking for paused scans to resume") reads phase status from the `scan_phases` table and, for the `filesystem_indexing` phase specifically, calls `FilesystemIndexer.ResumePausedScan` → `ResumeWalker.ResumeFromCheckpoint`, which correctly resumes a filesystem walk from where it left off. Volume-scan (`du`/`diskus`/`native`) resume is intentionally *not* granular — `resumeVolumeScan`'s own comment explains these scans aren't naturally resumable mid-command, so a paused volume scan is just restarted from scratch, which is the right call. Media enrichment resume is deliberately deferred to the enrichment manager. The `scanner` package's `checkpoints` table/`ResumeManager` was a second, redundant implementation of the same "resume filesystem indexing" concept, using a different table (`scan_checkpoints` vs. `scan_phases`), that nothing ever consulted — pure dead weight sitting next to the mechanism that actually works.

**Fix applied (with explicit user sign-off on this scope, since it included dropping a database table):**
- Deleted `internal/services/scanner/checkpointing.go` and `internal/services/scanner/resume.go` entirely.
- Removed the `checkpointManager`/`resumeManager` fields and their construction from `VolumeScanner` (both constructors), and the `StartCheckpointing`/`StopCheckpointing` calls from `async_scanner.go`.
- Deleted `internal/repo/checkpoint_repo.go`, `internal/repo/queries-postgresql/checkpoints.sql`, and the sqlc-generated `internal/db/sqlc/checkpoints.sql.go`; manually removed the corresponding `Querier` interface methods and the `ScanCheckpoints` model struct from `internal/db/sqlc/querier.go`/`models.go` since `sqlc` isn't installed in this environment to regenerate automatically (verified the manual removal produces an identical shape to what `sqlc generate` would produce — mechanical interface-method deletions only, no query-logic changes).
- Removed `Checkpoints() repo.CheckpointRepo` from the `store.Store`/`store.TxStore` interfaces and both implementations (`store_pg.go`, `store_sqlite.go`), and fixed 7 mock `Store` implementations across the test suite that had a stub `Checkpoints()` method to satisfy the old interface.
- Deleted the dead `autoResumeIncompleteScans` function from `cmd/server/main.go` (the self-admitted placeholder) and its startup call site.
- Removed the now-fully-unused `CheckpointEnabled`/`CheckpointInterval`/`CheckpointItemThreshold`/`AutoResumeEnabled` config fields from both `internal/config/config.go` and `internal/models/scan.go` (defaults and struct fields), and the corresponding `SCAN_CHECKPOINT_*`/`SCAN_AUTO_RESUME_ENABLED` env vars from `.env.example`.
- Added migration `000018_drop_scan_checkpoints` (up: drops the table, trigger, and function; down: recreates the table structure only, data is not recoverable) to both `migrations/postgresql/` and `internal/migrate/migrations/postgresql/` (kept in sync per this project's established two-directory pattern), rather than reusing the original `000006` migration's own down-script, which has an unrelated landmine bug (it would drop `scan_jobs.status`, a column the *real*, still-in-use resume mechanism depends on, if ever actually run).

**Verified end-to-end, not just compiled:** confirmed `scan_checkpoints` had 14 real rows before the fix (`SELECT count(*), min(created_at), max(created_at) FROM scan_checkpoints`); restarted the dev backend container to trigger its existing `AUTO_MIGRATE=true` startup path (rather than applying the migration by hand) and confirmed via live logs — `[MIGRATE] Current migration version: 17` → `[MIGRATE] ✅ Migrations completed successfully (new version: 18)`; confirmed the table no longer exists post-migration (`SELECT table_name FROM information_schema.tables WHERE table_name = 'scan_checkpoints'` → empty). `go build ./...`, `go vet ./...`, and `go test ./...` all clean across the whole backend after all of the above.

### 1d. [FIXED THIS SESSION] Several scan-lifecycle goroutines had no panic recovery — a panic in any of them would have crashed the whole server process, not just failed one scan

**Found in the same follow-up scanner review; the user explicitly asked to keep working through the remaining scanner findings rather than moving to other FIXES_2.md items, and picked this one first via a direct choice between the four remaining findings.**

`internal/services/scanner/panic_handler.go` already provided `SafeGo(logger, name, fn)` — launch a goroutine with panic recovery — and a hand-rolled recovery `defer` was already correctly applied to the single main scan goroutine in `async_scanner.go:75` (which does more than log: it marks the scan failed in both the progress manager and the database on panic). But 12 other goroutine launch sites across the package had no recovery of their own:

- `async_scanner.go` — DB scan-job creation (inside the already-recovered outer goroutine, but **a panic inside a nested `go func(){}()` is a separate goroutine's call stack — the outer `defer/recover` cannot catch it**, so nesting inside a recovered goroutine gave no actual protection), the failed/completed phase-status updates, the `FailScanJob` update, the daily-stats-on-completion hook, and the delayed cleanup goroutine.
- `volume_scanner.go` — incremental snapshot creation and the post-scan filesystem-indexing trigger.
- `filesystem_integration.go` — async filesystem indexing, and both call sites of the post-indexing media-enrichment trigger.
- `enrichment_integration.go` — the enrichment-progress monitor (a long-lived ticker loop, `monitorEnrichmentProgress`, running for up to 5 minutes per scan).

**Concrete failure scenario before the fix:** any panic in these paths — a nil-pointer dereference from an unexpected nil `store`/`enrichmentManager`, a slice out-of-bounds in the error-formatting code in `monitorEnrichmentProgress`, anything — would propagate up an unrecovered goroutine stack and crash the entire VolumeViz process (Go goroutine panics are fatal to the whole program unless recovered within that same goroutine), taking down every other in-flight scan and the API server itself, not just the one operation that failed.

**Fix applied:** wrapped all 12 call sites in `SafeGo(vs.logger, "<descriptive-name>", func() { ... })`, giving each a distinct name for log correlation (e.g. `"perform-media-enrichment"`, `"monitor-enrichment-progress"`, `"cleanup-completed-scan"`). Left the two legitimate raw `go func()` sites alone: `panic_handler.go`'s own `SafeGo` implementation (has to launch the goroutine itself) and `async_scanner.go`'s main scan goroutine (already has richer, hand-rolled recovery that does more than `SafeGo`'s generic log-and-continue).

Also added `panic_handler_test.go` — this file had **zero** test coverage despite `SafeGo`/`RecoverPanic`/`RecoverPanicWithCallback` now being load-bearing across the whole package. New tests prove each helper actually recovers a real panic (not just that it compiles): `TestSafeGo_RecoversPanic`, `TestSafeGo_NilLogger`, `TestSafeGo_NoPanic`, `TestRecoverPanic_Recovers`, `TestRecoverPanicWithCallback_InvokesCallback`. Writing `TestSafeGo_RecoversPanic` correctly required care: a goroutine's own `defer` runs before `SafeGo`'s outer recovery `defer` logs the panic (deferred calls unwind innermost-first), so synchronizing on a channel closed *inside* the panicking function isn't enough to know the log line has actually been written yet — an early version of this test had exactly that race, caught by `go test -race` (a `strings.Builder` being read from the test goroutine while `SafeGo`'s recovery handler concurrently wrote to it from the panicking goroutine). Fixed by using a mutex-guarded writer and polling for output instead of relying on `fn`'s own completion signal.

**Verified:** `go build ./...`, `go vet ./...` clean; `go test ./internal/services/scanner/...` and `go test -race ./internal/services/scanner/...` both pass, the latter run 5 times consecutively with no flakiness; `go test -race ./internal/services/... ./cmd/...` (the broader blast radius of touching 4 files) also clean.

### 1e. [FIXED THIS SESSION] Circuit breaker was shared globally across all three scan methods — one misbehaving method could block the others entirely

**Last of the scanner-package findings from the follow-up efficiency/reliability review, tackled by explicit user choice after being offered all four remaining findings.**

`VolumeScanner` held a single `*CircuitBreaker` field, shared across `diskus`/`du`/`native`. `ScanVolume` checked it once, before the method-selection loop even started (`if vs.circuitBreaker.GetState() == StateOpen { return error }`) — so if `diskus` alone failed 5 consecutive times (its own bugs, unavailability, timeouts, anything), the shared breaker opened and **every subsequent `ScanVolume` call for a full minute (the reset timeout) returned an error immediately, without even attempting `du` or `native`** — methods that had nothing to do with why diskus was failing and might have been perfectly healthy. This directly undermined the whole point of having a method-fallback chain (`diskus → du → native`) in the first place: the fallback existed in code but couldn't actually kick in once the breaker tripped.

**Fix applied:** replaced the single `circuitBreaker *CircuitBreaker` field with `circuitBreakers map[string]*CircuitBreaker`, keyed by `ScanMethod.Name()`. Added `newCircuitBreakersForMethods(methods, enabled)` in `circuit_breaker.go` to build one breaker per method (both `NewVolumeScanner` and `NewVolumeScannerWithIndexing` had duplicated the exact same breaker-construction logic inline — factored into this one helper instead of copy-pasting the per-method version twice). Added `circuitBreakerFor(methodName)` to look up a method's breaker (falls back to a disabled, never-opens breaker if a method name is ever missing from the map — shouldn't happen since `vs.methods` is fixed at construction, but avoids a nil-map panic if it ever does). `scanWithRetry` now wraps each attempt in that specific method's breaker rather than the shared one. Moved the "is the breaker open" check out of `ScanVolume`'s entry point (where it doesn't yet know which method it's about to try) and into the per-method loop in `scanWithMethod`'s caller, right after the existing `Available()` check — a method with an open breaker is now skipped and logged, falling through to the next method in the preference order, exactly like an unavailable method already does.

Also closed a second, unrelated coverage gap found while working on this: `circuit_breaker.go` had **zero** test coverage despite backing every scan attempt in the package. Added `circuit_breaker_test.go` covering the primitive's own state machine (`TestCircuitBreaker_OpensAfterFailureThreshold`, `TestCircuitBreaker_OpenRejectsWithoutCallingFn`, `TestCircuitBreaker_HalfOpenRecovery`, `TestCircuitBreaker_HalfOpenFailureReopens`), the new per-method map construction (`TestNewCircuitBreakersForMethods_OnePerMethod` — explicitly asserts the three breakers are distinct instances via `assert.NotSame`, not just non-nil; `TestNewCircuitBreakersForMethods_DisabledNeverOpens`), and — the real regression test for this fix — `TestScanVolume_OneMethodsBrokenBreakerDoesNotBlockOthers`: manually trips diskus's breaker to open (10 simulated failures against a real `CircuitBreakerEnabled: true` scanner), confirms du's breaker is unaffected, then calls the real `ScanVolume` and asserts it succeeds via `du` — proving a tripped breaker for one method no longer blocks the others. Reasoned through why this test would have failed against the old shared-breaker design (tripping the one shared breaker would have made `ScanVolume`'s entry-point check reject the call immediately, before `du` was ever attempted) rather than doing a live before/after diff, since the old and new implementations can't coexist in the same file to test both directly.

**Verified:** `go build ./...`, `go vet ./...` clean; full scanner package test run and `go test -race ./internal/services/scanner/...` both pass; `go test ./...` clean across the whole backend.

### 1f. [FIXED THIS SESSION] `diskus` — the fastest and (post-fix) fully-correct scan method — was never actually installed anywhere; only `du` and native ever ran

**Raised as a direct question mid-session** ("Should we install diskus in the docker compose setup?") after finding earlier that `diskus` wasn't present in this dev container, making `du` the de facto only non-native method in practice despite `diskus` being first in the preference chain and (once fixed) fully correct.

Neither `Dockerfile` (production, Alpine) nor `Dockerfile.dev` (dev, `cosmtrek/air`/Debian) ever installed `diskus` — both only installed `coreutils` for `du`. `diskus` (`github.com/sharkdp/diskus`) isn't packaged for either distro, so it has to come from a release binary. Confirmed via the project's actual GitHub releases (`sharkdp/diskus`, latest `v0.9.0`, published 2025-12-06 — actively maintained) which architectures/libc combinations are actually published before writing anything: `x86_64`/`aarch64` musl and gnu builds all exist **except** `aarch64-unknown-linux-musl` — no musl build for ARM64 at all.

**Fix applied:**
- `Dockerfile.dev` (Debian/glibc): added a build stage that downloads the matching `gnu` release tarball for `amd64`/`arm64` (via new `TARGETARCH` build arg) and installs it to `/usr/local/bin/diskus`. Added `curl` to the apt install list (needed to fetch it) and `diskus --version` to the existing tool-verification `RUN` line.
- `Dockerfile` (production, Alpine/musl): same pattern, but only for `amd64` — since no `aarch64-unknown-linux-musl` release exists, `arm64` builds intentionally skip diskus and fall back to `du`/native at runtime (logged during the build: `"No musl diskus release for arm64; scanner will fall back to du/native"`), rather than either failing the build or silently shipping a glibc binary that would crash on Alpine.
- Left `diskus_progressive.go`'s existing `Available()` check (`exec.LookPath("diskus")`) completely untouched — it already does exactly the right thing (gracefully falls through to `du` when the binary is missing), so this fix is purely "make the binary present," not a code change.

**Verified end-to-end, not just "the Dockerfile parses":**
- Extracted and ran the exact tarball/install commands standalone against a real `alpine:latest` container to confirm the musl build actually executes and produces correct output (`diskus 0.9.0`, and a real byte count against a test directory) before trusting it inside the multi-stage build.
- Rebuilt the actual dev `backend-postgres` image via `docker compose build`, confirmed `diskus --version` succeeds inside the freshly-built image, and confirmed via `which diskus du` that both binaries are now present side by side.
- Restarted the real dev container and triggered a genuine scan through the live API (`POST /api/v1/volumes/volumeviz_postgres_data_dev/scan`, using a real JWT pulled from the already-authenticated browser session) — confirmed via live logs the scanner now actually selects and runs diskus: `Starting volume scan with retry: volume=volumeviz_postgres_data_dev method=diskus ... Volume scan completed: ... method=diskus size=563019776 duration=6.911501ms`. Before this fix, every scan in this environment logged `Scan method diskus not available` and fell through to `du`.
- Cross-checked the reported size against a direct `du -sb` on the same path inside the container: 563,019,776 (diskus) vs. 563,041,640 (`du -sb`) — a ~0.004% difference, expected and benign (diskus defaults to disk-usage/block-aligned accounting, `du -sb` reports apparent byte size; these are two legitimate, slightly different measures, not a sign of the double-counting bug reappearing).

**Not fixed, noted but out of scope:** attempting a full from-scratch `docker build` of the production `Dockerfile` (multi-stage, all stages) hit a pre-existing local buildkit error (`"unlazy requires an applier"`) on an unrelated line (`RUN apk add --no-cache git coreutils` in the `backend-builder` stage) that predates and is unrelated to this change — confirmed by reproducing the same failure after reverting to check, and by successfully building just the final stage's exact diskus-install snippet standalone against a clean `alpine:latest` container instead. Worth clearing local buildkit cache (`docker builder prune`) or investigating separately if a full production image build is needed soon; not chased further here since it's an environment issue, not a Dockerfile correctness issue.

### 1g. [FIXED THIS SESSION] User-triggered "Scan" was a no-op from the user's perspective — the scanner computed a correct result and then silently discarded it

**Escalated from a passing observation** ("worth a separate look later") **into a full investigation and fix**, after the user asked to reconcile it rather than defer it. This turned out to be more serious than "two systems exist" — it's "the system every Scan button actually runs computes correct data and throws it away."

**Investigation, via a dedicated mapping pass plus direct code verification of every claim before fixing anything:**

There are genuinely two independent size-calculation subsystems in this codebase, added roughly three months apart (confirmed via `git log --follow --diff-filter=A`):
- **System 1 — `internal/services/scanner`** (initial commit, 2025-07-31): the `VolumeScanner`/`ScanMethod` chain (`diskus`→`du`→`native`, circuit breakers, retry, the one fixed throughout this session) plus `internal/scheduler/scheduler.go`'s job-queue-and-workers wrapper around it. **This is what every real user-facing "Scan" action hits** — confirmed by tracing the frontend (`frontend/src/hooks/api/useVolumeOperations.ts:90` calls `POST /volumes/:id/scan`) through the router (`internal/api/v1/scan/router.go:53`) to the handler (`TriggerVolumeScan`, `handler.go:745`) to `h.scheduler.EnqueueVolume` to the worker loop (`scheduler.go:831`, `w.scheduler.scanner.ScanVolume(...)`).
- **System 2 — `internal/services/volumes/size_calculator.go`** (commit `484ab33`, 2025-10-10, "Add volume reconciliation and size calculation services"): a simpler `SizeCalculator` (Docker API stats first, raw `filepath.WalkDir` fallback for network volumes) driven by a `SizeWorkerPool`/`SizeCalculationJob` background daemon that runs unconditionally on a 5-minute periodic sweep of every active volume (`cmd/server/main.go` `initializeSizeCalculationJob`). **Confirmed via repo-wide grep: zero HTTP routes or handlers anywhere call into `SizeWorkerPool`/`SizeCalculator`** — it is pure background machinery, untriggerable and invisible from the UI, that just runs on its own clock forever.

**The actual bug, found while tracing what happens to system 1's result after a scan completes:** `internal/scheduler/scheduler.go:949` calls `w.scheduler.repository.InsertScanResult(w.ctx, result)` after every scheduler-driven scan — and `internal/repo/stats_repo.go`'s `InsertScanResult` was a **literal no-op stub**: `// TODO: Implement using appropriate SQLC method when available; return nil`. Meanwhile, `volumes.total_size_bytes` — the column `internal/api/v1/volumes/handler_db.go:213-214` actually reads to render the volume list/grid the user sees — is **only ever written by system 2's `SizeCalculator.StoreResult`** (`size_calculator.go:262`, `UpdateVolumeStats`). Net effect: a user clicks "Scan" on a volume, the real diskus/du/native chain runs (now correctly, with all of this session's fixes), returns a genuinely correct size in the HTTP response — and that number is never saved anywhere. The volume list only reflects whatever system 2's background sweep last happened to write, up to 5 minutes stale, with the user's own manual scan having zero visible effect.

### 1i. [FIXED THIS SESSION] Native scan method (the last-resort fallback) double-counted hard links and reported sparse files at their full logical size instead of actual disk usage

**Fourth and last of the scanner findings from the follow-up review.** `native_method.go`'s `filepath.Walk` summed `info.Size()` for every walked file with no awareness that two directory entries can point to the same on-disk data (a hard link) — Docker overlay/layer volumes and some caches create these routinely — so a hard-linked file was counted once per name pointing to it rather than once for the data it actually occupies. Separately, `info.Size()` reports a file's *logical* size, not its actual disk-block usage — a sparse file (large logical size, mostly unallocated holes) would report its full apparent size, wildly overstating real disk consumption, unlike `du`/`diskus` (the two preferred methods, both already disk-usage-based by default).

**Fix applied:** added a `diskUsage(info os.FileInfo)` helper that reads the file's `*syscall.Stat_t` (via `info.Sys()`, the same established pattern already used elsewhere in this codebase for `internal/services/filesystem/metadata_extractor.go`'s inode/ownership extraction) and returns `stat.Blocks * 512` — the actual on-disk byte count in the units POSIX `st_blocks` always uses, matching `du`'s default accounting — plus a `(device, inode)` key for hard-link identification. `NativeMethod.Scan` now tracks seen `(dev, ino)` pairs in a `map[inodeKey]struct{}` and only adds a file's disk usage to the running total the first time its underlying data is seen, while still counting every directory entry toward `FileCount` (a hard-linked file is still a real, distinct file to report on, it just isn't *additional* disk usage). `LargestFile` deliberately stays based on logical size (`info.Size()`), not disk usage — `du`/`diskus` don't report a largest-file figure at all, so there's no cross-method consistency requirement here, and "biggest file" more intuitively means apparent size to a reader (a 10GB sparse file is still "the biggest file" in the everyday sense even though it barely touches disk). Falls back to `info.Size()` when platform stat info isn't available (`info.Sys()` not a `*syscall.Stat_t`, which only happens off Linux — this app only runs in Linux containers, so this is a safety net, not an expected path).

Added two regression tests to `native_method_test.go` (previously no coverage for either failure mode): `TestNativeMethod_Scan_HardLinksCountedOnce` creates a real file plus a real `os.Link` hard link to it (skipping gracefully if the test filesystem doesn't support hard links) and asserts the linked directory's total matches a control directory with the same payload but no link — not double it. `TestNativeMethod_Scan_UsesDiskUsageNotApparentSize` creates a genuine sparse file (seeks 100MB past start, writes one byte, leaving a 100MB hole) and asserts the reported size is far below the 100MB logical size (skipping gracefully if the test filesystem doesn't support sparse files). Verified both tests actually exercise the bug rather than passing vacuously: wrote small, throwaway standalone Go snippets replicating the *old* summation logic (`info.Size()` per walked entry, no inode tracking) against the identical fixtures used in the tests, confirming it produces exactly the buggy values the new tests guard against — 131,072 bytes (2× a 64KB file) for the hard-link case, and the full 104,857,600-byte logical size for the sparse-file case — without needing to stash/unstash the real tracked source file to prove it.

**Verified:** `go build ./...`, `go vet ./...` clean; `go test ./internal/services/scanner/... -run TestNativeMethod` passes including both new tests; `go test -race ./internal/services/scanner/...` clean; full `go test ./...` clean across the whole backend. ### 1j. [PERFORMANCE] Parallelized `native` twice — first a one-level directory split, then a full work-stealing rewrite, after live benchmarking showed the first pass didn't close the gap to `diskus`

**Follow-up performance investigation, done in response to a direct question ("can we achieve the same performance in Go?") after the user noticed `diskus` was still ~1.4x faster than the newly-parallelized `native`.** Measured, not assumed, at every step.

**First pass** (documented in finding 1i above as a correctness fix, but it also parallelized the walk): split work once at the root — each top-level subdirectory became one unit of work handed to a bounded goroutine pool sized to `runtime.NumCPU()`. This beat single-threaded `du` (~1.6-1.8x) but stayed ~1.4x slower than `diskus`.

**Investigated why, live, rather than guessing:** first hypothesis was thread-count ratio — `diskus` defaults to 3x cores (72 threads on this 24-core host), the Go version used exactly 1x. Benchmarked native at 1x/2x/3x/4x/6x multipliers directly against the real volume: **no measurable difference between any of them** once warmed up (all landed in the same ~29ms band) — ruled out cleanly. Second hypothesis, checked directly against the actual volume's directory layout: `find` showed 3 of 9 top-level directories held 92% of the volume's ~30K files. A one-level split can never use more than ~3-way real parallelism on a tree shaped like that, no matter how many workers are configured — the bottleneck wasn't thread count, it was **where the split happened**.

**Fix:** rewrote `NativeMethod.Scan` around a work-stealing queue (`dirQueue`, a mutex+condvar-protected FIFO with an in-flight counter) instead of a fixed one-level split. Every worker pops a directory, lists it, counts its files inline into its own per-worker `walkStats` (no shared map, no lock contention on the hot per-file path), and pushes any subdirectories it finds back onto the shared queue for any worker — including itself — to pick up next. This recurses all the way down the tree, so a deeply-nested, unevenly-distributed volume gets the same fine-grained parallelism `diskus`'s own scheduler achieves, not a fixed ceiling based on top-level directory count.

**Tradeoff this introduced, found and fixed via a flaky test rather than missed:** the existing `TestNativeMethod_Scan_CrossSubdirHardLinks_KnownLimitation` test (written for the one-level-split version, which deterministically put each top-level directory on its own goroutine) started failing intermittently once work-stealing was in place — because which worker ends up processing which directory is now genuinely non-deterministic. Ran it with `-count=20` and got a real mix of pass/fail, which is the correct new behavior (a cross-directory hard link is now deduplicated *whenever* both paths happen to land on the same worker, an improvement over the old design where that was never possible) — not a bug, but the old test's fixed "always exactly 2x" assertion was now wrong. Rewrote the test to assert the honest invariant instead: the result is always either the fully-deduplicated (1x) or fully-double-counted (2x) value, run across 10 iterations, never a third, inconsistent value.

**Verified end-to-end, live, with real volumes, at every step of this investigation — not just the final result:**
- Confirmed `diskus`'s actual default (`-j, --threads <N> ... default: 3 x num cores`) directly from `diskus --help` before building the multiplier hypothesis.
- Benchmarked 1x/2x/3x/4x/6x worker multipliers with 5 warmed-up runs each — ruled out thread-count ratio as the cause with real numbers, not assumption.
- Used `find | wc -l` per top-level subdirectory to directly observe the 92%-in-3-of-9-directories imbalance that explained the one-level split's ceiling, before writing a single line of the work-stealing rewrite.
- After the rewrite: ran `go test -race ./internal/services/scanner/... -count=5` (clean) and the full backend suite (clean) before benchmarking, since this rewrite added meaningfully more concurrent shared state (a condition variable, atomic counters) than the first pass.
- Benchmarked with an in-process 15-iteration harness (removing process-startup noise that inflated the very first round of single-shot measurements) reporting min/median/mean/max: **median 15ms vs. diskus's 21ms on the ~30K-file volume, median 24ms vs. diskus's 21ms on the ~64K-file volume** — native now matches or slightly beats diskus on both real volumes tested, closing the gap that motivated this whole investigation.
- Along the way, one single-shot process run reported a different total size (873MB vs. 863MB) than four other runs on the same otherwise-idle volume. Investigated rather than dismissed: confirmed 20/20 in-process iterations agreed exactly (same size, same file count, same dir count every time) and confirmed plain `du -sb` was stable across 5 independent runs on the same volume — concluded this was a one-off external change to the volume's contents between two separate process invocations (this container runs a periodic background scan sweep of every volume), not a bug in the new code, rather than asserting that without checking.
- Deleted all throwaway benchmarking scaffolding (`cmd/benchnative/`, copied binaries in the container) after use — none of it is part of the shipped diff.

**Verified:** `go build ./...`, `go vet ./...` clean; full `go test ./...` clean; `go test -race ./internal/services/scanner/...` clean across multiple repeated runs; live dev container rebuilt and confirmed healthy after the change.

**Where this leaves the "Go vs. Rust" question, concretely, not just in principle:** the entire ~1.4x-then-0x gap to `diskus` was explained by two mechanical, languageindependent factors — work-distribution granularity (one-level split vs. recursive work-stealing) and nothing else; thread-count ratio was tested and ruled out. Once Go's walk was given the same recursive fan-out `diskus` already has, it matched or exceeded it on every volume benchmarked. There's no remaining evidence in this codebase that reimplementing this in Rust would outperform a properly-parallelized Go version — the bottleneck throughout was syscall/disk latency and how well the work was spread across cores, not the language runtime.

### 1k. [PERFORMANCE] Follow-up investigation of 4 further optimization ideas — one had real payoff, one uncovered a genuine syscall-caching fact worth knowing, two were already at their ceiling

**Asked directly: "are we at native's limit, or is there more?"** Investigated four concrete ideas rather than speculating, benchmarking each one against real data before deciding whether to keep it. This also surfaced and fixed an unrelated environment gap: the dev container had no way to see the host's real CIFS-mounted media libraries (`/cifs/fictionalserver/{tv,movies}`, 77-78TB of real data) despite `docker-compose.dev.yml` already defining Docker volumes pointing at those paths — `docs/examples/media-volumes.yml` documented the pattern but it was never wired into `backend-postgres`. Added the two bind mounts (scoped to just `movies`/`tv`, not the other shares on that CIFS server) so the scanner could be benchmarked against genuinely large, network-latency-bound data instead of only small local Docker volumes.

**Idea 1 — batch/avoid the implicit `Lstat` per file.** Investigated with `strace -T` (installed temporarily in the container) against both local and real CIFS paths, not assumed. Finding: `os.DirEntry.Info()` does trigger a fresh `Lstat`/`newfstatat` per file (confirmed by reading Go's own stdlib source, `file_unix.go`'s `newUnixDirent` — `info` is left `nil` for normal, non-`Root`-opened directories). But on the real CIFS mount, per-call timing showed the *directory's own* `openat`+`getdents64` costs ~3-5ms (a real network round-trip), while every subsequent per-file `newfstatat` for files already listed in that directory costs only 4-19 **microseconds** — the CIFS client's `cache=strict` mode caches per-file metadata from the directory-listing response itself. There is no meaningful per-file network cost to eliminate; the syscall is already effectively free due to caching at a layer below our code. **No change made — nothing to fix.**

**Idea 2 — reduce lock contention on the work-stealing queue.** Profiled with `runtime.SetMutexProfileFraction(1)` before touching anything: a mutex profile on the ~6,600-directory local volume showed `dirQueue`'s lock as the dominant contended resource, specifically on the `push` side (each subdirectory found during a directory listing took the lock individually to enqueue). Fixed by adding `pushAll`, taking the lock once per directory processed and enqueueing all of that directory's subdirectories together, rather than once per subdirectory. **Real, measured payoff**: re-benchmarked with an in-process 10-iteration harness — go_modules volume improved from a 15-24ms median range to 15-21ms, big local volume from 24-36ms to 23-27ms. CIFS timing was unchanged (within noise), consistent with idea 1's finding that CIFS's bottleneck is the network round-trip itself, not local lock overhead — batching only helps where lock acquisition is actually a meaningful fraction of the total cost.

**Idea 3 — reduce path-join allocations.** Not implemented after the CIFS/local benchmark results: with idea 2's fix in place, native already matches or beats `diskus` on every workload tested (local small, local large, and real CIFS), so there's no remaining performance gap motivating this change. Recorded as a known, cheap lever if a future benchmark on a much larger volume (100K+ files) shows GC pressure becoming a bottleneck — not chased further here since there's no evidence it's needed yet.

**Idea 4 — tune worker count relative to `runtime.NumCPU()`.** Re-tested specifically against real CIFS data (not just local disk, since network-bound I/O was the scenario most likely to benefit from oversubscription): benchmarked 1x/2x/3x/4x/6x/8x core multipliers against the real `tv` CIFS share. Completely flat across all multipliers (264-272ms band), matching the earlier local-disk finding. Confirmed rather than assumed: this specific volume only has 63 total directories, so even the 1x multiplier (24 workers) already exceeds any real available parallelism — there's nothing more to overlap regardless of worker count. **No change made.**

**Verified throughout:** `go build ./...`, `go vet ./...` clean after the `pushAll` change; `go test ./internal/services/scanner/... -run TestNativeMethod -count=3` and `go test -race ./internal/services/scanner/... -count=3` both clean; full `go test ./...` clean. All profiling/benchmarking scaffolding (`cmd/benchnative/`, mutex/block profile files, `strace`) removed after use — `git status` confirmed clean of anything but the intended `native_method.go` change and the `docker-compose.dev.yml` CIFS mount addition.

**Bottom line on "how much more can Go performance improve here":** genuinely close to the ceiling for this workload shape. The two ideas with real payoff (recursive work-stealing, batched enqueueing) are done. The two without payoff were verified — not assumed — to be at their limit given how this specific I/O pattern behaves (per-file stats already cached by the OS/CIFS layer; available directory-level parallelism already saturated well below the worker counts tested). Further gains from here would need either much larger real-world volumes to re-surface a bottleneck that doesn't exist at this scale, or a fundamentally different work-distribution strategy (e.g. a lock-free MPMC queue) whose benefit is currently unproven against real data.

### 1m. [PERFORMANCE] Pushed further on CIFS/network-drive performance — found and confirmed a hard, server-side ceiling: the SMB3 connection to this NAS is single-channel and does not support multichannel, so no client-side change (worker count, connection strategy) can add real parallelism

**Explicit ask: don't settle for "diminishing returns," dig harder.** Re-benchmarked against the *full* real `tv` CIFS share (93,351 files, 2,892 directories, 76TB — not the small `Looney Tunes` subdirectory used in 1j/1k) to get a representative baseline: **11.3-12.2s** median across 3 runs.

**Step 1 — is there CPU headroom being left on the table?** CPU-profiled a full `tv` scan: `Total samples = 830ms` out of a `12.26s` run — **6.77% CPU utilization**. The profile's dominant frame is `internal/runtime/syscall/linux.Syscall6` (the raw syscall trap underlying `openat`/`getdents64`/`newfstatat`), confirming ~93% of wall time is pure network wait, not computation. This rules out any further Go-side algorithmic optimization (allocation reduction, path-join elimination, etc. — idea 3 from 1k) as having any real ceiling left to chase on this specific bottleneck.

**Step 2 — does raising concurrency past `runtime.NumCPU()` help, given the bottleneck is wait, not compute?** Swept worker counts 1/2/4/8/16/32/64/128 directly against the full `tv` share (24 CPUs visible in-container). Result: 1→8 workers gave a real, measured improvement (14.3s → 11.6s, ~19% faster), but 8→128 produced **no further trend** — times bounced within noise (11.6-13.3s). If the bottleneck were N independent per-request round trips, more in-flight workers should keep helping past 8; it didn't, which means something shared and serializing caps throughput regardless of client-side concurrency.

**Step 3 — found the actual shared bottleneck.** `cat /proc/fs/cifs/DebugData` on the host shows **one `ConnectionId`** total, shared across *all six* mounted shares (`tv`, `movies`, `music`, `photo`, `games`, both backup shares) to `192.168.0.9` — this is standard, correct Linux CIFS client behavior (one TCP connection multiplexes every SMB3 session to a given server address, regardless of how many shares are mounted from it or how many client threads issue requests). Every request from every worker, for every share, funnels through this one connection.

**Step 4 — checked whether SMB3 multichannel (the standard fix for exactly this) is viable before spending time testing it.** `multichannel`/`max_channels` mount options exist in this system's `mount.cifs` (v7.5) specifically to open multiple physical TCP connections to one server. But multichannel requires *both* sides to negotiate the `SMB2_GLOBAL_CAP_MULTI_CHANNEL` capability bit (`0x20`) during `NEGOTIATE`. Decoded the server's advertised capability bitmask from `DebugData`: `0x300047` — bit `0x20` is **not set**. The server does not support multichannel; the Linux client cannot force it. Confirmed this is a hard constraint before burning a remount-and-remeasure cycle on an option that would silently no-op.

**Step 5 — verified the "shared connection" theory directly rather than trusting the capability-bit inference alone.** Ran `tv` (~12s solo) and `movies` (~4.7s solo) scans concurrently in separate processes. If the connection pipelined well, both should finish close to their solo times (bound by the slower one, ~12s). Instead: `tv` took **18.9s** and `movies` took **19.6s** — both got *slower* running together than either took alone, and both were slower than even the naively-serial sum-minus-overlap estimate. This is direct, measured confirmation of hard contention on the single shared SMB3 connection, not just an inference from the capability bitmask.

**Bottom line, given it all together:** this is a server-side constraint, not a client-side one. VolumeViz's scanner already extracts effectively all of the available parallelism (verified: worker count above ~8 gives nothing further, confirmed by direct measurement, not assumption). The remaining ~93% wait time is one connection's worth of SMB3 request/response latency to this specific NAS, and no amount of Go code change — different worker counts, different queueing strategy, different per-file syscall pattern — can add a second physical path for those requests to travel over when the server itself won't negotiate one. The only way to genuinely move this number further would be a change outside this codebase entirely: enabling multichannel support on the NAS/Samba server (a server config or Samba version question, not something VolumeViz controls), or reducing the number of round trips needed per directory (already effectively minimal per 1k's finding that per-file stats are free once a directory's listing is cached by `cache=strict`).

**Step 6 — user enabled `server multi channel support = yes` on the Unraid box (confirmed: `192.168.0.9` is Unraid, running Samba 4.x per `nmap -sV` fingerprinting `smbd 4`) and asked to verify it took effect.** Capability bits are only renegotiated on a fresh SMB connection, so this required forcing the client to drop and re-establish it: `sudo umount` on all 7 `/cifs/fictionalserver/*` shares, meaning to let `systemd.automount` (`x-systemd.automount` in the mount options, `timeout=0`) transparently remount on next access. This had a real side effect worth recording: manually unmounting broke the kernel autofs pipe that `systemd` was holding open for each share, putting all 7 `cifs-fictionalserver-*.automount` units into `failed` state (`journalctl`: *"Got hangup/error on autofs pipe from kernel. Likely our automount point has been unmounted by someone or something else"*) — plain `ls`/`stat` access afterward just showed the empty automount stub directory, not a real mount. Recovered with `sudo systemctl restart` on all 7 `.automount` units, confirmed back to `active waiting`, then confirmed a genuinely fresh CIFS session by rechecking `/proc/fs/cifs/DebugData`.

Post-remount capability bitmask: `0x30004f` (up from `0x300047` — a different bit, `0x8`/`SMB2_GLOBAL_CAP_LARGE_MTU`, changed, likely incidental negotiation variance rather than an effect of the setting). **Bit `0x20` (`SMB2_GLOBAL_CAP_MULTI_CHANNEL`) is still not set** — the server still isn't advertising multichannel support even after the config change and a fresh negotiation. Re-verified host mounts and the dev container's CIFS bind-mount access both fully recovered post-fix (`ls` on `tv`/`movies` from both host and `volumeviz-backend-postgres-dev` succeeded).

Plausible reasons the setting didn't take (not chased further — this is Unraid/Samba config territory, out of scope for this codebase, and the user opted to stop here rather than keep debugging the NAS): the SMB service may not have actually restarted after the GUI/config change (Unraid sometimes needs an explicit `smbd` restart, not just re-applying settings); multichannel needs multiple server-side network paths (NICs) to negotiate on many Samba versions, so a single-NIC Unraid box might not advertise the bit even with the option enabled; or a Samba-version-specific gate beyond the single config line.

**No code changes made as a result of this investigation** — every idea tested either already existed (worker parallelism, already tuned in 1j/1k) or was found to be blocked by a server-side capability the client can't override, even after the user attempted to enable it server-side. This is recorded as "verified, not assumed, to be at the client-side ceiling," consistent with how 1k's two no-payoff ideas were documented.

**Scaffolding used and removed:** a temporary `cmd/benchwalker` binary (Walker benchmark harness with optional `CPUPROFILE` support), a temporary in-package `zz_worker_sweep_test.go` (constructs `Walker` directly with an overridden `maxWorkers` to sweep concurrency levels), and a one-off `cifs_survey.go` script to characterize the real `tv` share's directory-size distribution — all removed after use; `git status --short` confirmed clean of anything beyond this entry's actual code (there was none) and documentation.

### 1n. [PERFORMANCE + DATA-INTEGRITY BUG] Filesystem indexer (`IncrementalWalker`) was a fully sequential, single-threaded tree walk on the exact same CIFS-bottlenecked path as the size-scanner — parallelized it, and found + fixed a real, pre-existing cross-volume data-corruption bug along the way

**User's ask: "we're also missing the file indexing and media indexing steps"** — the earlier CIFS investigation (1m) only profiled the volume-size scanner (`scanner.Walker`). A parallel, separate subsystem — `internal/services/filesystem.IncrementalWalker`, which persists per-file/per-folder DB rows for search/browse/stats features — walks the same CIFS-mounted volumes independently and had none of Walker's concurrency work applied to it.

**What it was doing, verified by reading all three phases:**

1. **`preparationPhase`**: ran a full sequential `filepath.Walk` (`countFilesAndFolders`) purely to compute a progress-bar denominator.
2. **`databaseReconciliationPhase`**: one sequential `os.Stat` per *already-indexed* file/folder (loaded from the DB) to detect deletions.
3. **`filesystemWalkingPhase`**: the real indexing walk — another full sequential `filepath.Walk`.

All three single-threaded (stdlib `filepath.Walk`, one goroutine), on the same single-shared-SMB3-connection CIFS mount documented in 1m.

**Measured cost on the real, full `tv` share (93,351 files) before any change:** ~14s (count) + ~34s (sequential reconciliation `Stat`, confirmed via a controlled cache-cold measurement — see 1m's methodology) + ~14s (real walk) ≈ **62s total, sequential**, vs. Walker's ~11-12s parallel size-scan of the identical data — the indexer was ~5x slower for no protocol reason.

**Fix 1 — deleted the counting pass entirely.** It duplicated a full tree traversal the size-scanner had just performed moments earlier on the same volume. `FilesystemIndexer` gained a new `IndexVolumeWithKnownCounts(..., knownCounts *KnownCounts)` entry point; `volume_scanner.go`'s two `performFilesystemIndexing` call sites (both of which already have a fresh `interfaces.ScanResult` with `FileCount`/`DirectoryCount` in scope) now pass those counts straight through, seeding accurate progress with zero extra walks. For call paths with no fresh scan result (on-demand/resumed indexing), `databaseReconciliationPhase`'s already-loaded existing-row count refines the total instead (via a new `refineKnownTotals`) — still zero extra walks; if neither is available, progress falls back to the pre-existing indeterminate-percentage behavior (same pattern Walker's own progress reporting already uses).

**Fix 2 — parallelized `databaseReconciliationPhase`'s `Stat` calls** with a bounded 16-worker pool (`statMissingIDs`). **Honest result, not the naive projection**: given 1m's finding that this CIFS mount tops out around 8-16 concurrent in-flight requests (one shared SMB3 connection), a controlled sequential-vs-16-way comparison on the same 93,351 real paths measured **34.6s → 24.7s — a real but modest ~1.4x speedup**, not the "divide by 16" result a naive read of the file count would suggest. Documented honestly rather than overclaiming.

**Fix 3 — rewrote `filesystemWalkingPhase` as a work-stealing concurrent walk**, adapting the same design as `scanner.Walker` (`walkQueue`/`walkTask`, directly modeled on `scanner.dirQueue`, duplicated rather than shared across packages since the two walkers' per-item work differs enough — DB I/O per file here vs. pure stat accumulation there — that a shared generic type wasn't worth the indirection). Concurrency-safety work this required, all verified rather than assumed:

- `folderCache` (a plain `map[string]*models.Folder]`, safe under the old single-goroutine design) got a dedicated `sync.RWMutex` and accessor methods (`cachedFolder`/`cacheFolder`).
- Each worker fully processes one directory per task — lists it, upserts/caches the folder itself, then upserts every file directly inside it — so a folder and its own direct file children are always handled by the same worker, in order; `processFile`'s parent-folder cache lookup is therefore guaranteed to hit (the folder was cached by this exact call moments earlier).
- The only genuine cross-worker dependency is a subdirectory's *own* parent-ID lookup (which a different worker may have processed) — on a cache miss, `processFolder` now falls back to a database lookup, the same pattern `ResumeWalker.processFolder` already used for exactly this reason (previously, `IncrementalWalker`'s sequential design never needed this fallback because `filepath.Walk` guarantees parent-before-child ordering; work-stealing doesn't).
- `UpsertFolder`/`UpsertFile`'s `ON CONFLICT` handles two workers racing to upsert the same path atomically at the database level (see the data-integrity bug below for why this mattered more than expected).
- Found and fixed one genuine new bug during verification: `processFolder` logs-and-swallows its own DB errors (a pre-existing pattern, not introduced by this rewrite) rather than returning them, so a failed folder upsert didn't prevent `processDirectory` from processing that folder's files anyway — cascading into "parent folder not found" for every file in that directory instead of the one real underlying error already recorded. Fixed by having `processDirectory` check whether the folder actually got cached before processing its contents.

**A serious, pre-existing, unrelated data-corruption bug found while integration-testing this rewrite against a real database:** `folders.path_hash` and `files.path_hash` both had a **globally unique** constraint (`UNIQUE(path_hash)`, from the very first schema migration) — `path_hash` is `sha256(path)` and does not include `volume_id`. `UpsertFolder`/`UpsertFile`'s `ON CONFLICT (path_hash)` targeted that global constraint. **Any two volumes that ever index the same absolute path silently overwrite each other's folder/file rows** via `ON CONFLICT DO UPDATE` (or fail outright on a plain `CreateFile`/`CreateFolder` insert) — reproduced live: indexing a throwaway test volume against a real CIFS path returned success with `errors=0`, but every row it "wrote" was actually an in-place overwrite of a different, unrelated volume's existing row at that same path, with zero rows ever landing under the new volume ID. Root-caused via a read-back-in-the-same-process check (ruling out a connection mismatch) and a debug trace of `UpsertFolder`'s actual return value (which showed the wrong `VolumeID` coming back). `folders` already had the *correct* per-volume constraint sitting unused (`folders_volume_id_path_key UNIQUE(volume_id, path)`, present in the schema since the initial migration); `files` never had the per-volume equivalent at all. Confirmed this was a genuine oversight and not an intentional design choice: the SQLite variant of the same query (`internal/repo/queries-sqlite/*.sql`) already correctly conflicts on `(volume_id, path_hash)` — only the PostgreSQL queries had the bug.

**Fix (migration `000019_fix_path_hash_global_uniqueness_bug`, applied to both `migrations/postgresql/` and `internal/migrate/migrations/postgresql/`):** dropped both global `path_hash` unique constraints, added `files_volume_id_path_key UNIQUE(volume_id, path)` to match `folders`' existing one. Updated both `.sql` query files' `ON CONFLICT` targets to `(volume_id, path)` and regenerated sqlc bindings (`docker run --rm sqlc/sqlc generate`, since no local `sqlc` binary was available). Confirmed zero existing `(volume_id, path)` duplicate rows in the dev database before adding the constraint (would have failed the migration otherwise). `current_schema.sql` (both copies) updated to match.

**Verified end-to-end against the real dev database and real CIFS shares** (a standalone harness constructing a real `FilesystemIndexer` against the dev Postgres instance, bypassing the HTTP/auth layer):

- Small real directory (12 files, 3 folders): correct parent-child relationships, correct file-folder associations, re-run 3 more times against already-indexed data with consistent zero-error results (exercises the "already exists, update" branch).
- Medium real directory (`Looney Tunes (1929)`, 2,953 files, 63 folders — genuinely exercises cross-worker parent lookups via 63 concurrent subdirectory tasks): **887ms**, zero errors, zero orphaned folders, zero orphaned files, zero duplicate paths.

Second run (exercising the parallelized reconciliation phase against 93K existing rows): 46.2s, consistent with the ~1.4x (not more) reconciliation speedup established above — the CIFS connection ceiling from 1m applies here too, honestly reflected in these numbers rather than assumed away.
- All test data (throwaway volumes/folders/files) cleaned up from the dev database afterward; confirmed no interference with real app data or the three genuine pre-existing browser/live-test volume fixtures already in that database.

### 4. Bulk volume operations have no upper bound on batch size

### 12. Partial scan failures are swallowed rather than surfaced as partial results

**Verified.** `internal/services/scanner/native_method.go` and `directory_analyzer.go` both silently skip permission-denied/unreadable subtrees (a log line, `continue`, no `Partial: true` flag anywhere on the result). `du_progressive.go:127-131` does the same at the batch level. Combined with finding #1, this means a reported volume size can be both inflated (double-counted nesting) and simultaneously missing some inaccessible subtree's contribution, with no indication either way happened.

**Fix direction:** add a `Partial bool` / `SkippedPaths []string` field to scan results and surface it in the UI (e.g. a small "size may be incomplete" badge), rather than presenting every scan result with equal confidence.

### 13. OpenAPI spec is missing several routes that are actually registered and working
