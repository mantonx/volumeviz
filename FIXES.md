**Date:** 2026-07-10
**Source:** Full-app audit (parallel code review of every page + live registration/login test against a fresh Docker Postgres instance). Companion to `PROJECT_STATUS.md` (narrative/toolchain-health doc) — this is the actionable punch list, organized by severity.

Each item has enough context to act on without re-deriving it. File:line references are as of this audit; re-check before fixing since line numbers drift.

## P0 — App-breaking (blocks basic usage)

### 0. [FIXED THIS SESSION] `customFetchClient` returned the wrong response shape — silently broke Dashboard, Sidebar, VolumeDetailsPage, ExplorerPage, and SearchPage regardless of how much real data existed

**The single biggest finding of this session — verified live with a full round-trip through the actual browser, not just API-level testing.**

`src/api/fetch-client.ts`'s `customFetchClient` (the orval mutator every generated hook/query calls) returned the raw parsed JSON response body directly. But orval's generated TypeScript types (`httpClient: 'fetch'` mode) have always modeled every endpoint's response as a discriminated union keyed on the real HTTP status — e.g. `getVolumesResponse200 = { data: PagedResponse; status: 200 }`. Several components were written correctly against these generated types, checking `.status === 200` before accessing `.data` — but since the actual mutator never produced that envelope, `.status` was always `undefined` on every response, so `.status === 200` was always `false`, and every one of these components permanently fell through to its empty/fallback state — no matter how much real data the backend actually returned. This wasn't a component-logic bug; the components were correct against the types, the runtime just never matched the types it claimed to implement.

Confirmed affected (i.e. every file using the `.status === 200` pattern against the old, unwrapped mutator): `Dashboard.tsx` (all 3 stat/org/alert queries — the empty "Welcome to VolumeViz!" state you'd see on every login, even with real volumes), `Sidebar.tsx` (the "Total Volumes: 0 / Active Volumes: 0" quick-stats that never updated), `VolumeDetailsPage.tsx`, `ExplorerPage.tsx` (file listing), `SearchPage/AdvancedFilters.tsx`, `SearchPage/DuplicateDetectionModal.tsx`, `hooks/useAlerts.ts`, `components/domain/explorer/Charts/VolumeCharts.tsx`.

**Fix applied:** changed `customFetchClient` to wrap successful JSON responses as `{ data: <body>, status: response.status, headers: response.headers }`, matching what the generated types already promised. Error responses are unchanged — the client still `throw`s a `FetchError` on non-2xx, so none of the app's existing try/catch or TanStack Query `isError`/`error` handling needed to change.

This is a real, intentional architectural convergence, not a patch — 14 other files that had been written against the *old* (raw-body) behavior needed migrating to the new shape (unwrap one extra `.data` level) since they now receive the envelope too:

- `LoginPage.tsx` — 1 change (unwrap `response.data` for the login payload)
- `FilesPage.tsx`, `FileTable.tsx`, `FileGrid.tsx`, `ApiHealthChecker.tsx` — unwrapped correctly, following the same discriminated-union pattern already used elsewhere
- `hooks/api/useVolumesList.ts` — unwrapped correctly; **also caught and fixed a second, independent real bug in the same pass**: the pagination-computation code assumed a nested `{data, pagination: {page, page_size, total}}` body shape, but the real API returns flat `{data, page, page_size, total, filters}` fields — confirmed against a live `GET /volumes` call. Both bugs were masking each other (the wrapper mismatch meant this code path never even ran against real data before), so neither could have been caught without fixing the wrapper first.
- `hooks/useTrends.ts` — 3 call sites unwrapped (this also means `TrendsPage`'s `storageGrowthData`/`trendStats` should now compute from real trend data instead of an always-empty/undefined body — `fileTypeData`/`capacityForecast` remain genuinely empty per the separate, real backend gap already documented in `PROJECT_STATUS.md`, not this bug)
- `RegisterPage.tsx`, `UserProfilePage.tsx`, `MountsPage.tsx`, `RulesPage.tsx`, `VolumesPage.tsx`, `OnboardingPage.tsx`, `useVolumeOperations.ts`, `useVolumeRowActions.ts`, `useVolumeBulkActions.ts`, `FileMetadataDrawer.tsx` — confirmed to need **no** change (either use raw `fetch()` directly, not the generated client, or only consume mutation results for `onSuccess`/`onError` side effects without reading the resolved body, or — `FileMetadataDrawer.tsx` specifically — were already written correctly against the wrapped shape).

**Verified end-to-end in a real browser session** (not just API-level curl testing): fresh login → Dashboard now shows `Total Volumes: 72`, `Tracked Volumes: 72`, `Total Size: 20.84 GB`, `Orphaned Volumes: 70`, a real volume in "Recent Volumes" — matching the live backend exactly. Sidebar "Quick Stats" also now shows `72` instead of the permanent `0`. `npx tsc --noEmit -p .` after all changes: 0 real (non-test/story) errors.

### 1. [FIXED THIS SESSION] Two migration files were never embedded into the binary — broke registration, login, and volume tracking

**Verified directly against a running instance, root-caused, fixed, and re-verified.**

The real bug (my first two theories below turned out to be downstream symptoms, not the cause — see "false leads" at the end of this item): `internal/migrate/migrate.go` uses `//go:embed migrations/postgresql/*.sql`, which embeds `internal/migrate/migrations/postgresql/` — a **separate copy** of the migrations directory from the top-level `migrations/postgresql/`. The two had drifted: `000015_add_volume_metadata` and `000016_add_volume_tracking` existed only in the top-level directory and were never copied into the embedded one, so they have **never run in any environment built from this binary**, including production, presumably, if it was ever deployed past this point.

Consequence: the `volumes` table was missing `driver`, `scope`, `labels`, `options`, `is_tracked`, `tracked_at`, `untracked_at` — columns the generated `sqlc` code and Go repo layer have referenced for a while. This caused:

- Continuous volume-reconciliation failures (`column "driver" does not exist`) on every scan cycle, for every real Docker volume on the host — confirmed in backend logs against ~75 real volumes.
- The `users_organization_isolation` RLS policy on `users` rejecting registration inserts (a downstream effect, not really an RLS design gap — see false leads).
- **Volume track/untrack likely never worked in any environment running off this migration state**, despite this session having written passing integration tests for it — the tests use MSW mocks and never touched a real, correctly-migrated database, so they couldn't have caught this.

**Fix applied:** copied `000015`/`000016` `.up.sql`/`.down.sql` into `internal/migrate/migrations/postgresql/`, rebuilt, ran against a fresh database. `AUTO_MIGRATE: "true"` was also missing from `docker-compose.dev.yml`'s backend service and has been added — without it the backend just logs a warning and skips migrations entirely, meaning anyone following the documented dev workflow starts from an empty schema. Verified end-to-end: `POST /auth/register` now returns `201` with a real user; `POST /auth/login` returns `200` with a real JWT; reconciliation errors are gone from the logs.

**Remaining follow-up:** add a CI check (or a Makefile target) that fails if `migrations/postgresql/` and `internal/migrate/migrations/postgresql/` ever diverge again — this will silently recur otherwise. Also: **audit whether any other embedded/duplicated resource directories in this repo have the same drift problem** (this pattern — two copies of something that need to stay in sync — already bit the project once this session with `docs/swagger/` vs `docs/`).

**Also, separately — [FIXED THIS SESSION]:** the login page ships plaintext demo credentials (`demouser` / `NewPassword123`, `LoginPage.tsx:223-235`) that used to not correspond to any seeded user in a fresh database. Fixed properly, not just documented:

- Added a `healthcheck` to `backend-postgres` in `docker-compose.dev.yml` (hits `/api/v1/health`, which genuinely 503s until the DB is migrated and reachable — this didn't exist before, so nothing could reliably wait on "backend is actually ready").
- Rewrote `scripts/seed.sql`, which was stale against an old schema generation (wrong column names, referenced a `containers` table that doesn't exist, no `users`/`organizations` rows at all) — it now matches the real current schema and creates the `default` org, a `demouser` (role `admin`, password `NewPassword123`, hash generated by the real backend so it's guaranteed bcrypt-compatible) and two sample volumes so the dashboard isn't empty on first login. Idempotent (`ON CONFLICT ... DO NOTHING`), safe to re-run.
- Added a one-shot `seed` service to `docker-compose.dev.yml` that depends on `backend-postgres: condition: service_healthy` and runs `scripts/seed.sql` automatically.

**Verified from a genuinely cold start** (`docker compose -f docker-compose.dev.yml down -v` then `up -d --build postgres backend-postgres seed`, no manual steps): migrations ran, seed ran automatically after the healthcheck passed, and `demouser`/`NewPassword123` logs in successfully (`200`, real JWT) with no intervention. A new user cloning this repo today and running the documented compose command gets a working login.

**False leads worth recording** (so a future debugging session doesn't repeat this detour): my first hypothesis was that the registration endpoint needed to explicitly `SET LOCAL app.current_organization_id` before the RLS-protected insert, and that the `audit_organization_actions()` trigger had a separate bug (inserting into `audit_logs` without its `NOT NULL description` column). The audit-trigger bug **is real and still unfixed** — reproduced directly via `SET app.current_organization_id = '1'; INSERT INTO users (...)`, which hit `null value in column "description"` — but it's a latent no-op in normal operation (nothing in the request lifecycle currently sets that session variable), so it's demoted to a P2 item below rather than blocking anything today. Fix it before enabling real RLS enforcement, not before.

### 2. [FIXED THIS SESSION] Alerts subsystem silently disabled by default — Dashboard's alert banner was dead

**Verified live, root-caused, fixed, and re-verified.** Same shape of bug as `AUTO_MIGRATE`: `ALERTS_ENABLED` defaults to `false` (`internal/config/config.go:196`), gates whether `alertsEngine` is constructed at startup (`internal/api/v1/router.go:398`), which in turn gates whether the entire `/api/v1/alerts/*` route tree is registered at all (`router.go:406-409`) — with zero warning log when skipped (unlike the adjacent preview-service check, which does log a `[WARNING]`). `docker-compose.dev.yml` never set it, so `GET /api/v1/alerts` returned a bare `404` with no JSON body, and the Dashboard's active-alerts banner (`Dashboard.tsx:263-297`) — the first thing a user sees after logging in — silently never worked.

**Fix applied:** added `ALERTS_ENABLED: "true"` to `backend-postgres`'s environment in `docker-compose.dev.yml`. Verified: `[INFO] Alerts engine initialized successfully` and `[INFO] Alerts API routes registered successfully` now appear on startup; `GET /api/v1/alerts?status=firing` returns `200` with a real (empty, no rules configured yet) response instead of `404`.

**Follow-up worth doing:** add a startup warning log when `alertsEngine` is nil, matching the pattern already used for the preview service — silent route-skipping is exactly the failure mode that let both this and the migration-drift bug go unnoticed.

### 3. [FIXED THIS SESSION] Dashboard's "Tracked Volumes" stat used the wrong field

Found by comparing the Dashboard's computed stat against a real, live `GET /api/v1/volumes` response (only possible once the migration-drift bug above was fixed and `is_tracked` actually existed in the data). `Dashboard.tsx:83` computed `trackedVolumes` as `volumes.filter(vol => !vol.is_orphaned).length` — using "not orphaned" as a stand-in for "tracked," even though the real, typed `is_tracked` field (`VolumeV1.is_tracked`, confirmed in `src/api/orval-generated/api.ts`) has been available in the API client. Likely written before the migration that added `is_tracked` ever ran anywhere, and never revisited once it did.

This was invisible with the current seed data (every volume happens to have `is_tracked: true` regardless of orphan status) but would silently misreport the moment any real volume gets untracked via the UI's own "Untrack Volume" action.

**Fix applied:** `trackedVolumes = volumes.filter((vol) => vol.is_tracked).length`.

### 4. [FIXED THIS SESSION] Dashboard hardcoded `page_size: 100` for its volume-count stats — silently undercounts past the page limit

`Dashboard.tsx:38-48` calls `useGetVolumes({ page: 1, page_size: 100 })` and previously computed every stat tile (Total Volumes, Total Size, Tracked, Orphaned) client-side from just that fetched page — on a host with more than 100 Docker volumes (not hypothetical; this session's dev container watches a real host with 72, close to the limit), the stats would silently undercount past the 100th volume with no indication to the user that the numbers were partial.

**Fix applied (backend):** `GET /api/v1/volumes` already computed the full filtered set in memory before slicing to a page (both the DB-first path in `handler_db.go` and the Docker-API fallback in `handler.go` fetch/filter everything, then paginate at the end) — so no new DB query or endpoint was needed. Added a `summary` field to the response (new `models.VolumeListSummaryV1` — `total_volumes`, `tracked_volumes`, `orphaned_volumes`, `total_size_bytes`), computed via a shared `summarizeVolumes()` helper from the full filtered set in both code paths, before the pagination slice. Response type is now the dedicated `models.VolumesListResponse` (rather than the generic `apiutils.PagedResponse`) so swaggo/Orval generate a properly-typed field instead of `unknown`. Verified with a unit test (`page_size=1` against a 2-volume mock set asserts `summary.total_volumes == 2` while `data` has only 1 entry) and live via `curl ".../volumes?page=1&page_size=5"` against the real 72-volume dev host, confirming `summary.total_volumes: 72` while `data` only contains 5 records.

**Fix applied (frontend):** `Dashboard.tsx`'s four stat tiles now read `volumesData.data.summary.*` instead of deriving from the fetched page's `volumes` array. `page_size: 100` was deliberately left unchanged — it still governs the pool "Recent Volumes" picks its client-side-sorted top-5 from (see item 13), which is a separate concern from the stat-tile accuracy bug fixed here.

Same class of issue may still exist elsewhere in this doc (`volume_discovery.go:231`, `ExplorerPage.tsx:80`) — not fixed as part of this pass, worth checking with the same pattern (does the backend already have the full set in memory before paginating?) if revisited.

### 5. [FIXED THIS SESSION] `GET /api/v1/mounts` 500'd on every call with no query params — broke the onboarding wizard's real discovery, silently

**Verified live, root-caused, fixed, and re-verified.** `internal/api/v1/mounts/handler.go`'s `ListMountCatalogRequest` used `binding:"min=1"` on `Page`/`PageSize` — Gin binds an omitted query param to Go's zero value, and `min=1` then rejects it, so any call without explicit `?page=1&page_size=...` 500'd with `"Invalid query parameters"`. The handler already had working default-assignment logic for exactly this case (`if req.Page == 0 { req.Page = 1 }`, line ~149) — it just never ran, because binding validation failed and returned first.

This directly broke `OnboardingPage.tsx:339`, which calls `fetch('/api/v1/mounts')` with no params. The failed fetch left `mounts` empty, `transformMountDataToDiscovery` computed `totalMounts: 0`, and the page **silently substituted the hardcoded `mockDiscovery` fallback** (19 total mounts, 12 volumes, 6 bind, 1 tmpfs, fake compose project/service breakdowns) — with only a `console.log('No mounts discovered, using mock data for demo')` that no user would ever see. This is very likely why an early tester of this session saw the onboarding wizard show static-looking numbers that didn't match a real host.

**Fix applied:** changed the binding tags to `omitempty,min=1` (etc.) so an omitted param no longer fails validation before the existing default-assignment code gets a chance to run. Verified: `GET /api/v1/mounts` now returns real data (25 real mounts on this dev host, all `mount_type: volume`) instead of a 500.

**Now that real data flows through, two things about the "real" numbers are worth knowing, not further bugs, just context:**

- On this dev host, **24 of 25 mounts are orphaned** (`is_orphaned: true`) — no attached containers. The onboarding preview step's numbers will look much more dramatic with real data than the cheerful mock ever did. That's correct behavior, not a bug, but worth being aware of if a demo suddenly looks alarming.
- **[FIXED THIS SESSION]** No real mounts have a `compose_project` label set on this host, so the "Compose Projects"/"Top Services" panels were rendering their headings with zero rows underneath — not broken, `Object.entries({}).map()` just produces nothing, but it read as an unfinished/blank box. Added explicit empty-state copy ("No Docker Compose projects/services detected among these mounts.") to both panels (`OnboardingPage.tsx:759-782`).

**[FIXED THIS SESSION — see item 20 below]** The Preview step's client-side heuristic (`volumeCount + floor(bindCount * 0.5)`) has been replaced with a real call to the backend preview endpoint, using approach (b) described below: create the preset's rules for real, then preview them.

### 6. [FIXED THIS SESSION] `POST /api/v1/tracking/apply` 500'd on every real Docker host — onboarding's "Complete" step silently failed to apply any rules

**Verified live via the actual onboarding flow (create preset rules → apply), root-caused, fixed, and re-verified with 72 real changes applied successfully.**

`applyTrackingChanges` (`internal/api/v1/rules/handler.go:807-827`) tried `strconv.ParseInt(change.MountID, 10, 64)` to convert a mount identifier to the numeric ID `UpdateMountTrackingStatus` needs — but `change.MountID` (populated from `MountInfo.MountID` in `convertPreviewToChanges`, line 791) is the **Docker-facing mount identifier** (a volume name, often a 64-char hex string for anonymous volumes), not the mount catalog table's numeric primary key (`MountInfo.ID`, a completely separate field on the same struct). `ParseInt` on a hex volume name always fails, so `tracking/apply` 500'd on literally any real mount.

Consequence: `OnboardingPage.tsx:592-602` calls this endpoint but only `console.warn`s on failure ("Continue even if apply fails — user can apply rules manually") — so the wizard's "Complete" step always appeared to succeed (rules were created via `POST /rules`, which does work), the user was told their tracking preset was applied, navigated to the dashboard, and **none of their chosen volumes actually had their tracking status changed**. This is the same "swallowed failure, confident UI" pattern as several other findings in this doc, just deeper in the funnel — a user could complete the entire onboarding wizard and never know the last step silently did nothing.

**Fix applied:** look up the mount by its string `mount_id` via the already-existing `mountsRepo.GetMountByMountID(ctx, change.MountID)` to get the real numeric `ID`, then pass *that* to `UpdateMountTrackingStatus`. Verified end-to-end: created a real rule via `POST /rules` (`201`), called `POST /tracking/apply` (`200`, `changes_count: 72`, real mount IDs in the response, no error) — test rule cleaned up afterward.

### 7. [FIXED THIS SESSION] Onboarding's "Go to Dashboard" completion step never refreshed the Dashboard's cached data

**Verified live: created rules, applied tracking, navigated to Dashboard — confirmed stale data before the fix, real data after.**

`completeOnboarding` (`OnboardingPage.tsx:548-635`) POSTs rules and calls `tracking/apply` (item 6 above), then calls `navigate('/')` — but never invalidated the TanStack Query cache for the volumes/mounts queries it had just changed server-side. If the Dashboard's `useGetVolumes` query had already been fetched and cached (`staleTime: 5 minutes`) before `tracking/apply` ran, the user would land back on a Dashboard showing pre-onboarding data for up to 5 minutes, with no visual indication anything was stale.

**Fix applied:** `queryClient.invalidateQueries({ queryKey: ['/volumes'] })` and the equivalent for `/mounts`, called right before navigating. (Superseded in practical impact by item 8 below, which was the actual reason the Dashboard kept showing an empty state regardless of cache state — but this fix is still correct and worth keeping for the caching scenario it does address.)

### 9. [FIXED THIS SESSION] WebSocket real-time connection permanently missed the auth token on most sessions

**Verified live: confirmed the failure, root-caused it, fixed it, confirmed a real WebSocket connection succeeds afterward (backend log: "Broadcasting volume states to 1 connected clients").**

`RealtimeProvider` (mounted once near the app root, wrapping the entire `Router` including the login page) computed its authenticated WebSocket URL via `useMemo(() => { const token = localStorage.getItem('auth_token'); ... }, [websocketUrl])` — keyed only on `websocketUrl`, which never changes. Since the provider mounts before login happens, this memo almost always computed with `token: null` on its one and only run, and never recomputed after `login()` actually stored a real token — because the memo's only dependency never changed. Console showed a continuous `WebSocket connection ... failed: HTTP Authentication failed` retry loop (confirmed independently by a browser-automation pass and by directly reproducing it) for the lifetime of every session.

**Fix applied:** `useAuth()`'s `login`/`logout` now dispatch a `window.dispatchEvent(new Event('auth-token-changed'))` after updating `localStorage` (since `useAuth` is a plain hook, not a shared context — other components can't otherwise learn the token changed in the same tab). `RealtimeProvider` now tracks the token in local state, refreshed by listening for that event plus the native cross-tab `storage` event, and the WebSocket URL memo is keyed on that state instead of a one-time read.

**Verified:** a page reload after login now shows `[RealtimeProvider] WebSocket URL with auth token prepared` with zero auth-failure console errors, and the backend log confirms a real connected client receiving broadcasts. Note: the very first connection attempt during the login→redirect transition itself can still race (the event fires synchronously but `react-use-websocket`'s own connection lifecycle may already be mid-attempt) — a subsequent reload or the library's own `shouldReconnect` retry picks up the token correctly. Full elimination of that one-time transitional race would need `react-use-websocket`'s connection re-triggered explicitly on the event rather than relying on its default reconnect behavior; not done here since the practical impact (one failed attempt immediately followed by a successful one) is minor compared to the prior fully-broken state.

### 9b. [FIXED THIS SESSION] "Maximum update depth exceeded" React error, recurring every ~10 seconds on every page with an active WebSocket connection

This error had surfaced repeatedly throughout this session (originally exposed by item 9's WebSocket auth fix, then again during the Modal rewrite work, then again on `VolumeDetailsPage`) — it looked page-specific each time, but it was actually global background noise firing on a fixed interval, independent of whatever page happened to be open when it was noticed.

**Root cause, confirmed on both ends via live instrumented WebSocket capture** (a `WebSocket` constructor proxy that logged every real incoming message, not just reasoning from source): `internal/realtime/websocket_hub.go`'s `Hub.Run()` starts a `time.NewTicker(time.Second * 10)` that calls `broadcastCurrentVolumeStates()` on every tick. That function queried every volume on the host and broadcast **one fabricated `scan.status` message per volume** — hardcoded `"progress": 100.0` and `"message": "Current volume status"` regardless of whether the volume was scanning at all — to every client subscribed to `scan_progress_all`. On this dev host (72+ volumes) that produced a burst of ~80 messages within a few hundred milliseconds, every single connected client, every 10 seconds, for the life of the connection. `RealtimeProvider.tsx`'s `scan.status` handler wrote a real Jotai atom update for each `is_active: true` volume in the burst — enough synchronous state-update volume in one flush to trip React's guard. This is why it looked like it fired "randomly" on different pages: it wasn't triggered by anything page-specific, it was a recurring global tick.

This `scan.status` broadcast turned out to be **pure duplicate, fabricated noise** — investigation confirmed a real, already-fully-wired scan-progress pipeline exists (`VolumeScanner → ProgressManager → Broadcaster → Hub.BroadcastScanProgress`/`BroadcastScanEvent`, see `internal/services/scanner/progress_manager.go`), which emits genuine `scan.progress`/`scan.started`/`scan.completed`/`scan.failed` events **only while a scan is actually running** — and `RealtimeProvider.tsx` already had correct handlers for all of those. The periodic ticker's `scan.status` sweep was invented on top of a system that already did this correctly, and the "not actively scanning, so 100%" comment right next to the hardcoded `progress: 100.0` shows whoever wrote it already knew it wasn't reporting anything real.

**Fix applied:**

- **Backend** (`internal/realtime/websocket_hub.go`): removed the `scan.status` broadcast entirely from `broadcastCurrentVolumeStates()` (both the per-organization and system-admin branches) — it now only sends the real, accurate `volume.state` broadcast it already correctly produced. Real scan progress continues to flow through the existing, already-wired pipeline instead.
- **Frontend, defense-in-depth** (`RealtimeProvider.tsx`): all 14 of the file's `useWebSocketEventListener` calls were passing a fresh inline arrow function as their callback on every single render. `useWebSocketEventListener`'s effect depends on that callback (`[eventType, addEventListener, callback, ...dependencies]`), so a new identity every render forced a cleanup+resubscribe cycle 14 times per render — wasteful regardless of backend behavior, and exactly the kind of churn that turns a legitimate message burst into a synchronous update-depth violation. Replaced all 14 with individually memoized (`useCallback`, empty deps) relay functions, so a burst of real messages can no longer cascade the same way even if the backend ever legitimately needs to send one.
- Removed the leftover debug render-counter (`console.log('[RealtimeProvider] RENDER COUNT:', ...)`) now that the investigation it was left for is resolved.

**Verified live**: captured real WebSocket traffic via a `window.WebSocket` constructor proxy across two full 10-second ticks (25s window) on `VolumeDetailsPage` — `scan.status` message count: **0** (previously ~80 per 10s tick). Zero `"Maximum update depth exceeded"` console errors across that same window, and again on a separate 22-second idle check on the Dashboard. `go test ./...`: all pass. `npx tsc --noEmit`: 0 errors in either touched file.

### 9c. [FIXED THIS SESSION] Completing onboarding sent first-time users right back into onboarding

**Found during a dedicated, from-scratch onboarding walkthrough (fresh account, no prior state) — reproduced, root-caused, fixed, and re-verified with a second fresh account.**

`App.tsx`'s `shouldRedirectToOnboarding` is computed exactly once, in a `useEffect` with an empty dependency array, when the app first mounts. ### 12. [FIXED THIS SESSION] `Modal.tsx` drawer variant — four real bugs plus a full animation-engine rewrite

Found while building the Help drawer above — the underlying `Modal` component's `variant="drawer"` mode had never been exercised by a real feature before, so none of the following had been caught:

1. **Container flex-centering fought drawer positioning.** `containerClasses` unconditionally applied `flex items-center justify-center p-4`, which centers a modal — but a drawer positions itself via its own `fixed` + edge-offset classes, so the two fought and the drawer rendered centered instead of docked to an edge. Fixed by only applying the centering classes for `variant === 'modal'`.
2. **CSS cascade bug: `relative` beat `fixed`.** Both classes were present on the drawer element at different points; despite `fixed` being what the drawer variant needs, `relative` won because of Tailwind's generated-stylesheet rule order (not the order classes appear in the HTML `class` attribute — a common CSS-cascade footgun). Fixed by only applying `relative` for `variant === 'modal'`.
3. **Opaque black backdrop instead of translucent.** The backdrop used a dynamically-interpolated class name (`` `bg-opacity-${backdrop.opacity}` ``) — Tailwind's JIT scanner only detects literal class strings in source, never template-interpolated ones, so this class was never generated at all. Doubly broken since Tailwind v4 also removed the `bg-opacity-*` utility outright (replaced by `bg-black/50` slash syntax). Fixed by applying opacity via inline `style={{opacity: ...}}` instead of a dynamic class.
4. **Body scroll-lock caused a layout shift.** Locking scroll via `document.body.style.overflow = 'hidden'` removes the scrollbar, shifting all fixed-position content sideways by the scrollbar's width. Fixed by measuring `window.innerWidth - document.documentElement.clientWidth` and compensating with `padding-right` on the body while locked.
5. **The slide-in/out animation itself was fundamentally broken** — reported three times in a row during live testing ("doesn't slide out, just disappears", "too quickly", "still just disappears"). Root cause: the original state machine used `useEffect`-driven `isEntering`/`isExiting` booleans that inherently lag one render behind the `open` prop (effects run only after the render that triggered them commits) — so the render-gate that decided whether to keep the drawer mounted could unmount it before the exit-transition effect ever got a chance to run. Multiple incremental patches (Tailwind class fixes, `requestAnimationFrame` double-buffering, a `wasOpenRef` render-gate patch) each fixed a real distinct symptom but never addressed the underlying design flaw. **Rewritten from scratch** per explicit direction rather than patched further: replaced the four-boolean approach with a single `Phase` state machine (`'closed' | 'opening' | 'open' | 'closing'`) where unmounting is gated on the real browser `transitionend` event instead of a hand-tracked `setTimeout` duration guess (with a `setTimeout` fallback only as a safety net in case `transitionend` never fires, e.g. `display:none` ancestor).

**Verified live via instrumented Playwright trace** (real `getComputedStyle().transform` + `transitionend` timestamps, not just visual inspection): opening the drawer shows a genuine ~260ms animated transform from offscreen (`matrix(1,0,0,1,296.9,0)`) to docked (`matrix(1,0,0,1,0,0)`); closing shows the inline style flip to the offscreen transform, a real `transitionend` firing ~305ms later once the computed transform has fully animated to offscreen (`matrix(1,0,0,1,384,0)`), and DOM detachment only *after* that event — never before. Repeated open/close 3x in a row with no stuck state. `npx tsc --noEmit -p .`: 0 errors in `Modal.tsx`.

**Not fixed, noted but out of scope:** a real, pre-existing `"Maximum update depth exceeded"` React error was observed in the console during this verification, rooted entirely inside `react-use-websocket`'s internals (`webSocketInstance.onmessage → protectedSetLastMessage → flushSync`), unrelated to the Modal work. This is very likely the same infinite-render-loop class of bug already flagged as unresolved in item 9b above (`RealtimeProvider`'s leftover debug render-counter) — worth a dedicated investigation, not a Modal follow-up.

**Follow-up structural cleanup (same session):** once the rewrite was verified working, `Modal.tsx` (originally 692 lines carrying the state machine, style/class computation, and render logic all inline) was split into focused single-purpose files: `useModalPhase.ts` (the Phase state machine — the two near-duplicate `transitionend` effects for the entering/closing legs were also merged into one, parameterized by phase, removing ~20 lines of duplication), `useFocusTrap.ts`, `useBodyScrollLock.ts`, and `modalStyles.ts` (all the pure class/style-computation functions). `Modal.tsx` itself shrank to 370 lines of composition and render logic. Also deleted `Modal/components/{ModalHeader,ModalBody,ModalFooter}.tsx` — dead code from an earlier, abandoned compound-component design that was never imported anywhere (confirmed via grep) and sat alongside the real, actually-used inline render functions, which was actively confusing.

While fixing two Modal test failures uncovered during this cleanup (one asserting the old, already-removed `bg-opacity-75` class; one failing because `backdrop={{closable: false}}` doesn't include `show`), found and fixed a real, separate, latent bug: `backdrop` and `focusTrap` were both default *parameters* on the whole prop object (e.g. `backdrop = {show: true, opacity: 50, closable: true}`), which in JS only applies when the prop is omitted **entirely** — passing any partial object (`backdrop={{opacity: 75}}`) silently dropped `show: true`, so the backdrop stopped rendering. Fixed by merging field-by-field (`{show: true, opacity: 50, closable: true, ...backdropProp}`) instead. `npx tsc --noEmit -p .`: 0 new errors. `Modal.test.tsx`: 49/50 passing (up from 46/50 before this session's fixes) — the one remaining failure (`max-h-[500px]`) is a pre-existing, separate dynamic-Tailwind-class bug in the unused `maxHeight` prop, left as-is and documented in `modalStyles.ts` rather than fixed as an unrelated drive-by change.

### 13. [FIXED THIS SESSION] Dashboard's "Recent Volumes" surfaced meaningless anonymous system volumes instead of anything a user would recognize

### 25. [FIXED THIS SESSION] Multi-tenancy scope decision — cut down to single-org after a dedicated research pass, rather than guessing which direction was cheaper

**What the research found:**
- Real backend org-scoping machinery exists (JWT `org_id` claims, `middleware.RequireOrganization()`, ~13 of 20 sqlc query files filtering by `organization_id`) — but it's **never been exercised beyond org id 1** in this system's history. One organization, four users, zero seed data or migration implying a second org ever existed.
- **Registration is hardcoded to org 1 by explicit design, not oversight** — `RegisterPage.tsx` rendered a literal on-screen disclaimer ("Registering with organization ID 1 (default organization)") and a `<input type="hidden" value={organizationId}>` that, on inspection, wasn't even read by the submit handler (the request body pulled `organizationId` from React state directly) — pure dead markup.
- **No org-switcher UI exists anywhere, not even as dead/unused code.** Switching orgs would require re-authentication (org_id is baked into the JWT at issuance, not swappable client-side), not a context switch — so building one for real would be a genuine feature, not a small fix.

- A full Row-Level-Security layer is defined in the live Postgres schema (`CREATE POLICY` statements for volumes/files/folders/users/audit_logs) but **is a dead letter in practice** — the only code that ever calls `set_organization_context()` is wired into the router as `security.NewSecurityMiddleware(nil, r.store) // unused for now`. Nothing in the real request path ever activates it.
- The "RLS/registration bugs" this document previously alluded to were traced to their source: the actual registration-breaking bug (now fixed, see item 1) was two missing embedded migrations, not an RLS design gap. The one remaining RLS-adjacent defect (an audit trigger crash on a `NOT NULL description` column) is currently latent since nothing sets the session variable it depends on.

**Decision, made explicitly with the user after reviewing the above:** cut down to single-org rather than commit to finishing 20+ unscoped endpoints, wiring a dormant RLS layer, fixing 2 confirmed bypasses, and building a real org-switcher + multi-org registration flow for a use case with zero evidence it will ever be needed.
